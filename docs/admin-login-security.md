# 管理者ログインの安全対策

## 今回の変更

LPデザイン、無料相談フォーム、申込APIの挙動は変更していません。

- 管理者ユーザー名は `admin`。パスワードは起動時の環境変数 `ADMIN_PASSWORD` を使用します。ソースに本番用パスワードや既定パスワードはありません。未設定なら管理画面・一覧APIを503で閉じます。
- 認証情報を付けたリクエストが同じ接続元IPから5回連続で失敗すると、5回目から15分間HTTP 429を返します。誤パスワード、誤ユーザー名、不正な認証形式も対象です。
- `/admin` と `/api/applications` は失敗回数とロックを共有します。ロック中は正しいパスワードでも入れず、未認証リクエストにも申込情報を返しません。`Retry-After` ヘッダーで残り秒数を示します。
- ロック開始から15分後に解除します。ロック中のアクセスで解除時刻は延長しません。画面の案内は「15分後」と表示され、正確な残り秒数はヘッダーで返します。
- ロック前に認証が成功すると連続失敗数をリセットします。最後の失敗から15分間失敗がなければ、その履歴も期限切れにします。
- ブラウザが認証ダイアログを出すための、認証情報を付けていない最初のリクエストは失敗回数に含めません。
- SQLiteの `admin_login_attempts` に接続元IP・失敗回数・ロック解除時刻・最終失敗時刻だけを保存します。パスワードやAuthorizationヘッダーは保存しません。期限切れの履歴は次の管理者ルートへのアクセス時に削除します。
- アプリにパスワード・Authorizationヘッダーをログ出力する処理はありません。管理者レスポンスは従来どおり `Cache-Control: no-store` です。

## CookieとHTTPS

現在はBasic認証で、認証Cookie・セッションCookieを発行しません。そのため `HttpOnly`・`SameSite`・`Secure` の設定対象はありません。本番相当オプションでも `Set-Cookie` が付かないことをテストしています。

Basic認証の認証情報は暗号化ではなくBase64で送られます。公開するときは、必ずHTTPSのリバースプロキシで提供し、サーバーへの直接HTTPアクセスを外部から許可しないでください。`NODE_ENV=production` を指定するだけでHTTPSになるわけではありません。TLS終端や公開基盤の設定は今回実施していません。

ブラウザにBasic認証情報が残る性質や、明示的なログアウト・MFAがない点は従来どおりです。共有端末では使用せず、利用後はブラウザを終了してください。将来Cookie認証に変える場合は、その変更時にHttpOnly・SameSite・公開時のSecure・CSRF対策を実装します。

## 本番パスワードの設定手順（今回は未設定）

1. 利用予定のホスティングの秘密情報／環境変数設定画面を開きます。
2. 名前を `ADMIN_PASSWORD` とし、パスワード管理ツール等で生成した長く推測しにくい専用パスワードを、安全な値入力欄に設定します。例文やテスト用パスワードは使わないでください。
3. 公開時には `NODE_ENV=production` も設定し、HTTPSを構成します。今回、一般公開や外部デプロイは行っていません。
4. 設定を適用したプロセスを再起動します。認証画面にはユーザー名 `admin` と、ご自身が設定したパスワードを入力します。

パスワードはチャット・ソース・Git・スクリーンショットに記載しないでください。`.env` はローカル利用向けでGit対象外ですが、アクセス制限して扱う必要があります。`.env.example` は項目の見本だけです。本番の設定画面で、アプリのプロセスが実際の値を読める秘密変数として渡してください（外部API用のプロキシ認証とは用途が異なります）。

アプリ自身は認証情報をログに出しませんが、公開時のリバースプロキシや監視サービスでもAuthorizationヘッダー・環境変数の収集を無効化／マスクしてください。

## 制限の範囲

制限単位はソケットの接続元IPです。偽装された `X-Forwarded-For` 等で回避されないよう、そのヘッダーは信用しません。プロキシ配下では複数利用者が同じ接続元となり、一人の失敗で管理者全体が15分ロックされる場合があります。

この制限は分散したIPからの総当たりをすべて防ぐものではありません。公開基盤での管理者アクセス制限や、信頼できるプロキシ設定に合わせた制限は、公開構成の確定時に確認してください。同じDBを保持する限りロックは再起動後も継続しますが、DBの削除・古いバックアップへの復元では履歴が失われることがあります。

## 検証結果

`npm test`：7件成功、失敗・スキップ0。

- 従来の申込保存・入力検証・個人情報ファイル非公開・認証の回帰テスト。
- 無認証リクエストを繰り返しても失敗数に加算されない。
- 最初の4回は401、5回目から429。管理画面・APIで共通に制限。
- 正しい認証情報でもロック中は拒否。偽装転送ヘッダーでも解除されない。
- サーバー再起動後もロック継続。解除直前は拒否し、15分経過時に成功。
- 認証成功時の連続失敗数リセットと、15分間失敗がない場合の期限切れ。
- ロック中もLP表示と無料相談の申込が利用可能。
- 環境変数から読み込んだ検証用ランダムパスワードで認証成功。
- 成功／失敗レスポンス・ログに検証用秘密値がなく、認証Cookieも発行されない。

テストは一時DBまたはメモリDBで実行し、本番用パスワード・実際のお客様の情報は使用していません。15分の経過はテスト用時計で再現しています。既存の稼働中サーバーの再起動や本番設定の注入は行っていません。
