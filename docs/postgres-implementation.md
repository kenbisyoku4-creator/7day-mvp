# PostgreSQL対応の実装・検証

2026年11月5日（日本時間）。LPデザイン・フォーム項目・ブラウザ側のコードは変更していない。本番接続情報は登録・表示せず、Supabaseや外部DBへの接続・データ移行・一般公開を実施していない。

## 実装したこと

- `storage/postgres.js`：Nodeの `pg` ドライバーによる保存層。申込保存・一覧、ログイン制限履歴、接続確認、終了処理を実装。
- `storage/sqlite.js`：既存処理をローカル／テスト専用アダプターに分離。
- `server.js`：保存層を非同期で呼び出す。フォームと管理画面のAPI形式・既存認証・5回失敗／15分制限を維持。
- `migrations/001-postgres.sql`：専用の `money_private` スキーマと2テーブル。自動実行しない。管理用ロールで作成し、コメントに記載した最小権限をアプリ専用ロールへ付与する。アプリにはDDL権限を与えない。
- `package-lock.json`：依存を固定。依存導入は `npm ci`。

## 起動・設定

通常の `npm start` はPostgreSQL。秘密環境変数 `DATABASE_URL` がない／不正、証明書が検証できない、接続不可、必要なスキーマへアクセスできない場合は起動を中止する。失敗例外に接続文字列を含めず、SQLiteへ切り替えない。

既存のローカル確認を続ける場合だけ `npm run start:sqlite` と明示する。`.env` は自動で読まず、使用時は `node --env-file=.env server.js`。この場合も `STORAGE_BACKEND` を確認する。起動済みの旧プロセスは今回変更・再起動していない。

将来接続を許可する際は次を設定・確認する：

1. SupabaseのConnectでSession poolerを選び、専用DBロールのホスト・ユーザー名・DB名・ポートを確認する。接続文字列は秘密変数 `DATABASE_URL` だけへ保存する。
2. `STORAGE_BACKEND=postgres`（省略時もpostgres）を使用する。
3. TLSは常に `rejectUnauthorized: true`。必要な場合は、公式に取得したCA証明書をファイルに配置し `DATABASE_CA_CERT_PATH` で指定する。秘密鍵を指定しない。
4. URLのSSL設定が検証を弱めないよう、URLパラメーターは `sslmode=verify-full` だけを許可する。SSLパラメーターなしでもコードが厳格検証を設定する。`sslmode=require`・`disable`・`no-verify` 等や他のパラメーターは拒否する。コードへ `connectionString` をそのまま渡さず、接続先・資格情報を分解してTLS設定と分離する。
5. TCP経路・プーラーの証明書チェーン・DB権限を確認してからアプリを起動する。今回はこの実サービス確認を行っていない。

`ADMIN_PASSWORD` は従来どおり管理者画面用の別の秘密変数。Supabase AuthやCookie認証へは変更していない。

## 接続の上限

1プロセスにつきプール1個、最大3接続。接続待ち10秒、未使用接続30秒、SQL実行10秒、クライアント側クエリー待ち12秒、ロック待ち5秒、トランザクション内の無操作15秒。セッションプーラーで接続を専有することを考慮し、複数プロセス起動時は合計接続数を確認する。

終了時にプールを閉じる。トランザクション失敗時はROLLBACKし、ROLLBACKも失敗した接続は破棄する。生のドライバー例外や接続設定は出力しない。プールのアイドル接続エラーでも生の例外をログに出さない。

## 保存と認証の安全性

- SQLはパラメーター化。受付日時はTIMESTAMPTZで保存し、APIではISO文字列、IDはINTEGERの数値として既存画面に返す。
- ログイン判定はIPごとのトランザクションロックで直列化。初回の履歴行がない場合も同じIPの競合を防ぐ。複数アプリプールでも共有する。
- 正しいパスワードでも15分ロック中は拒否。成功時は失敗数リセット、同一IPの期限切れ履歴は次回アクセス時に削除。パスワード本体はDBへ保存しない。
- 別IPの古い履歴を一括削除する定期運用はまだない。公開時は期限切れ行の定期削除を計画する。削除は更新中の行と競合する可能性があるため、オフピーク・小分け実行など運用を検討する。
- DB障害時は管理者ルートを503で閉じ、申込保存失敗は従来どおり500と日本語メッセージを返す。成功が不明なINSERTを自動再試行しない。
- スキーマはPUBLICへ公開しない。SupabaseのData API公開対象から除外し、anon・authenticatedへの権限がないことを接続許可後に実測する。実サービスの既定権限は今回未検証。

## テスト結果

- `npm test`：**12件成功、失敗・スキップ0**。既存7件の回帰に加え、TLS・接続数・タイムアウト設定、危険なSSL上書きの拒否、設定なしの起動中止、閉じたローカルポートへの接続失敗、ROLLBACKと接続返却、DB障害時のHTTP応答を検証。
- `PG_TEST_BIN=... npm run test:postgres`：**4件成功、失敗・スキップ0**。PostgreSQL 17.11を127.0.0.1のランダムポートで一時起動し、実際のSQLとTLSで検証。
- 非同期化後も同時15件の申込のうち10件を保存し、5件を429で拒否することを確認。送信件数はINSERT前に予約し、保存失敗時に予約を解除する。
- 実PostgreSQLで申込INSERT・一覧API・同じDBへ再接続した後の保持を確認。
- 同じIPから10件を2つのアプリプールへ同時送信し、最初の4件は401、残り6件は429。再接続後のロック継続・15分後の解除・成功リセットを確認。
- 信頼していない証明書・ホスト名不一致の接続を拒否。サーバー側でもTLS接続を確認。アプリ専用ロールによるCREATE TABLEを拒否。
- PostgreSQLテストは環境に登録されたDATABASE_URLを使わず、固定のループバック接続先を組み立てる。使い捨ての架空データ、証明書、ローカルDBをテスト終了時に削除する。本番DBや実際のお客様の情報は使わない。

再実行にはNode.js 24、`npm ci`、ローカルのPostgreSQL 17バイナリとopensslが必要：

```sh
npm test
PG_TEST_BIN=/path/to/postgresql/bin npm run test:postgres
```

通常の `npm test` は外部DBもローカルPostgreSQLバイナリも必要としない。PostgreSQL実機検証は別コマンドにし、バイナリ未導入の場合は明示エラーにする（成功扱いのスキップはしない）。

ブラウザ回帰検証も一時SQLiteで実施し成功。幅320 / 390 / 760 / 1440pxでの表示、フォーム送信、管理者一覧、保存されたHTMLの無害化、保存失敗・502・通信失敗時の日本語表示と入力保持を確認した。LP・フォームのファイルに差分はない。
