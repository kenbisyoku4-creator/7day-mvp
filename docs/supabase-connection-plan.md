# Supabase：接続準備とSQLite移行設計

2026年11月5日（日本時間）。東京リージョンで作成済みのSupabaseを、**IPv4対応セッションプーラー**で利用する前提の設計。

今回はソースの確認と設定項目の準備だけ。DBへのDNS照会、TCP/TLS接続、認証、SELECT、テーブル作成、データ移行、一般公開はすべて未実施。接続情報の値も参照・出力していない。既存のLP・フォーム・サーバー実装は変更していない。

## 現在の構成と変更範囲

| 現在 | 移行時に必要な対応 |
| --- | --- |
| Node.js 24、外部依存なし、標準HTTPサーバー | 維持。PostgreSQL用の `pg` を将来導入し、バージョンとロックファイルを固定する。今回は未導入。 |
| `server.js` がHTTP・認証・SQLiteを一括処理 | 保存処理を別モジュールへ分離し、HTTPから非同期で呼び出す。 |
| `DatabaseSync` の同期処理 | PostgreSQLは接続プールと `await` に変更する。SQLiteのファイルパスをURLに変えるだけでは動かない。 |
| 起動時にテーブルを自動作成 | 管理用のマイグレーション工程に分離。通常のアプリ用DBロールにCREATE権限を与えない。 |
| `applications` のINSERT／一覧SELECT | パラメーター化したPostgreSQL SQLへ置換。既存の一覧順・上限500件を維持する。 |
| `admin_login_attempts` に5回失敗・15分ロックを保存 | 同じPostgreSQLへ移す。複数リクエスト時にも失敗回数・解除・成功リセットが競合しない設計が必要。 |
| `ADMIN_PASSWORD` によるBasic認証 | 維持。DB接続パスワードとは別管理。Supabase Authへの切替や認証Cookie追加は行わない。 |
| `public/` のフォームと管理者画面 | URL・入力項目・JSON形式を維持するので、表示変更は原則不要。 |
| SQLiteファイル・WAL・権限600 | 移行後は外部DBのTLS・権限・保存時暗号化・バックアップが保護の中心になる。旧SQLiteも移行完了まで保護する。 |

## 秘密環境変数

接続情報の名前は **`DATABASE_URL`** とする。

- 実際の値はホスティングの「秘密情報／シークレット」入力欄にのみ登録する。チャットやソース、公開用環境変数、画面、ログ、スクリーンショットには記載しない。
- `.env.example` には空欄の項目だけを追加済み。秘密値を含む `.env` と `.env.*` はGitから除外し、`.env.example` のみ追跡する。
- 現在の `server.js` はこの変数を読み込まない。現段階では登録しても自動接続・移行しない。
- 接続処理を実装した後は、環境変数を設定してアプリを再起動する必要がある。設定保存だけでは、起動中のプロセスへ確実に反映されたとは扱わない。
- `ADMIN_PASSWORD` は管理画面用、`DATABASE_URL` はサーバーからDBへ接続するためのもの。互いに同じ値を使わない。
- `SUPABASE_SERVICE_ROLE_KEY` やブラウザ用の公開キーは、このSQL接続方式では必要ない。接続情報をブラウザへ渡さない。
- パスワード部分の特殊文字は接続文字列に適したエンコードが必要。後から文字列を手作業でログ出力して確認せず、安全な設定画面で確認する。

**今回は秘密値を登録・置換していない。** ユーザーに接続文字列をチャットへ貼り付けてもらう必要もない。

## セッションプーラーの確認項目

将来、Supabase管理画面のConnectから **Session pooler** を選び、そこで示されるホスト・ポート・DB名・プーラー用ユーザー名を使う。通常の直接接続やTransaction poolerと混同しない。

- リージョンが東京であることを確認する。アプリも可能なら日本または近隣へ配置する。
- セッションプーラーは一般に5432番、トランザクション方式は一般に6543番だが、**必ず管理画面の指定を正とする**。ホスト名・プロジェクト識別子・ユーザー名を推測しない。
- IPv4対応という前提は利用者の選択内容に基づく。実際のDNS、通信経路、認証は今回は未検証。
- 作成時の強い管理ユーザーをアプリから常用せず、プーラーで使える最小権限の専用DBユーザーを準備する。そのユーザーに対応するプーラー用ユーザー名・パスワードを確認する。
- セッション方式では、アプリからの接続が維持されている間、DB側の接続も専有する。セッションプーラーを使っても接続数を無制限に増やしてよいわけではない。
- `pg.Pool` はプロセスごとに1つ。リクエストごとに新規プールを作らない。初期案は最大3接続、未使用30秒、接続待ち10秒、SQL実行10秒を上限。Supabaseの契約上限と同時プロセス数を確認して調整する。
- 終了時にプールを閉じる。アプリの一時的な再起動重複も接続数の予算に含める。
- プーラーが共有エンドポイントの場合、ネットワーク許可先は実際のプーラーホストに限定する。必要な5432等へのTCP許可と、クラウドの対応するTCP接続経路も次工程で確認する。HTTPドメイン許可だけではPostgreSQL接続できるとは限らない。今回はネットワーク設定を変更しない。

## TLSの設計

- 通信はTLSで暗号化し、サーバー証明書とホスト名を検証する。
- `rejectUnauthorized: false` や証明書検証を無効にする設定は使わない。
- Supabaseの対象エンドポイントに必要なCAは、その公式の案内から取得する。OSの信頼ストアで検証できる場合はそれを使い、専用CAが必要なら信頼できるファイルとして配置する。どちらが必要かは今回は未確認。
- `pg` は接続文字列中のSSLパラメーターと、コード側の `ssl` オプションが競合する場合がある。実装時にSSL設定を1つの検証済み経路へ統一し、URLのパラメーターで検証を弱められないことをテストする。
- エラーは「DBに接続できません」等の固定メッセージと安全な分類コードだけを表示。ドライバー例外・接続設定オブジェクト・環境変数・認証ヘッダーをそのままログに出さない。

## テーブルとSQLの対応

専用の非公開スキーマを使う案。Data APIの公開対象に含めず、`anon`・一般の `authenticated` ロールに読取・書込権限を与えない。SQL接続なので、RLSの有効化だけでアプリ用ロールの権限が自動的に適切になるわけではない。テーブル所有者とアプリ用ロールを分け、匿名APIとSQLロールの両方を検証する。

### applications

- `id`：PostgreSQLの `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` を初期案にする。現在のSQLite IDを保持でき、通常規模ではJSの安全な整数として扱える。移行前に既存IDがINTEGERの範囲内か確認する。超過時はBIGINT＋APIでのID型を明示的に設計する。
- `name`・`email`・`preference`・`message`：TEXT、NOT NULL。現行の長さ・選択値制約をDB側にも追加する案。`message` は空文字を許可する。
- `created_at`：TIMESTAMPTZ。現在のISO形式からUTCとして移行し、APIではISO文字列へ統一する。管理画面の日本時間表示は維持する。
- メールの一意制約は勝手に追加しない。同じ人の再相談があり得るため、重複防止が必要なら別途リクエストIDで設計する。
- PostgreSQLの `$1` 形式のパラメーターと `rows` へ変更する。SQLiteの `?`・`.run()`・`.get()`・`.all()` はそのまま使えない。
- 一覧は必要なカラムを明示し、新しい順に最大500件。認証成功前には問い合わせない。

### admin_login_attempts

- `client`：TEXT PRIMARY KEY。現行と同様、信用できない転送ヘッダーは使わない。
- `failures`：INTEGER。`locked_until`・`updated_at`：BIGINTのエポックミリ秒を初期案とする。
- PostgreSQLドライバーがBIGINTを文字列で返す場合、時間値を安全な整数範囲と確認してNumberへ変換する。文字列比較や暗黙の型変換に依存しない。
- 期限切れ確認、現在のロック確認、失敗加算または成功リセットは、同じクライアントの行を直列化するトランザクションで行う。初回行の作成も競合を考慮する。単純に各処理へ `await` を足すだけでは、並列リクエスト時の連続失敗数が壊れる可能性がある。
- トランザクション中は同じプールクライアントを使い、例外時はROLLBACK、必ず接続を返却する。
- DB障害でロック状態を確認できない場合は、管理者アクセスを拒否する。エラーを理由に認証を通してはいけない。

## アプリ側の変更案

将来のファイル分割案（今回は作成・接続していない）：

- `server.js`：HTTP・入力検証・既存認証を維持。保存関数を非同期で呼び出す。
- `storage/postgres.js`：接続プール、申込保存・一覧取得、ログイン制限のトランザクション。
- `storage/sqlite.js`：ローカル開発・回帰テストが必要な場合だけ明示的に選択する旧方式。
- `migrations/`：管理用のバージョン付きDDL。アプリ起動時に自動移行しない。
- 設定モジュール：`DATABASE_URL` の存在・形式を値を表示せず検証。将来DB移行を有効にした本番では、欠落・接続失敗時に起動を失敗させる。SQLiteへ黙って切り戻さない。

PostgreSQL対応後の保存失敗は既存の日本語エラーを返し、成功が確認されるまで完了表示しない。接続断で保存結果が不明の場合、無条件のINSERT再試行は重複につながるため行わない。管理画面の取得失敗は汎用エラーで閉じ、一覧の個人情報を残さない。

## 将来の移行順序

1. 別途承認されたら、依存導入・保存層分離・接続設定検証を実装する。
2. 検証用DBと専用ロールを準備し、DDL・権限を作る。秘密変数を登録する。
3. 明示的な許可後に接続を試す。最初は架空データのみで検証する。
4. TLS、匿名拒否、正しい管理者認証、5回失敗制限、同時アクセスを確認する。
5. バックアップ・復元と、再起動・再デプロイ後の保持を確認する。東京でDBを作成しただけでは、自動バックアップが利用可能・動作済みとは扱わない。実際のプランを確認する。
6. 既存データの移行対象を合意する。必要ならSQLiteの整合したバックアップを取り、一時受付停止・移行・件数やID等の照合を行う。
7. 明示IDでコピーした場合はPostgreSQLの採番シーケンスを調整し、次の申込で衝突しないことを確認する。管理者ロック履歴も継続か切替時の扱いを決める。
8. 接続先を切り替え、実データを表示しない確認方法で通しテストする。新DBへ書込み開始後、古いSQLiteへ無条件に戻すと新規申込を失うので、切戻し手順を別途用意する。
9. 公開はこの移行とは別の判断とし、勝手に公開しない。

## 次工程の受入条件

- `DATABASE_URL` がない／形式不正でも秘密値を出さず、安全に失敗する。
- TLS・証明書検証・IPv4セッションプーラー接続を確認する。
- 申込保存、一覧、再起動保持、ID・日時型の互換性を検証する。
- 未認証の管理者画面・APIを拒否し、ログイン制限が並列アクセスでも正しく継続する。
- DBへの匿名アクセスと過剰権限を拒否する。
- DB障害時も認証を迂回せず、フォーム失敗表示と入力保持が維持される。
- アプリ、ドライバー、ホスティングのログに秘密値や申込内容が出ない。
- バックアップから復元できることを実際に確認する。
