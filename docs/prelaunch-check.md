## 最小限の修正

1. Basic認証の形式とユーザー名 `admin` を明示的に検証。従来の「パスワードだけで判定する」処理を修正。
2. nullや配列のJSONを500ではなく400として拒否。
3. 通信断・非JSON応答を利用者向けの日本語で表示し、入力を維持。
4. 管理者一覧の再取得に失敗した場合、過去に表示していた個人情報を残さない。
5. SQLite本体を権限600で作成・利用。これはOSユーザー間の権限制御であり、暗号化ではない。

## SQLiteのデータ消失リスクと公開条件

| 状況 | 現在の性質・必要な対応 |
| --- | --- |
| 同じディスク上のプロセス再起動 | 保存される。テスト済み。 |
| 再デプロイ・コンテナ再作成・環境再構築 | ディスクが一時領域だとDBは消える。`data`を永続ボリュームに割り当て、公開環境で再起動・再デプロイ後の復元を検証する。Gitからは復元できない。 |
| マシン故障・誤削除・ディスク破損 | 永続ディスクだけでは保護できない。アクセス制限した別保存先へ定期バックアップし、復元テストを行う。暗号化と保持期限も決める。 |
| WAL運用 | 稼働中に本体だけコピーすると未反映データが欠落するおそれがある。SQLiteのバックアップAPIなど整合性のある手段を利用する。今回バックアップ先の構築や復元訓練は未実施。 |
| ディスク満杯・権限エラー | 保存に失敗する。利用者への失敗表示は検証済み。公開時は空き容量・保存エラーの監視が必要。 |
| 複数インスタンス | ローカルDBは別々になり、申込が分散・見えなくなる。初期公開は単一インスタンス＋永続ディスク。拡張時は共有DBを検討。 |
| スナップショットの巻き戻し | 復元時点以降の申込を失うおそれがある。復元点とバックアップ頻度を運用として決める。 |

## 残る公開前の課題

- HTTPSでのみ提供する。Basic認証は暗号化通信を前提とする。今回のHTTPはローカル検証用であり、本番のTLS終端は検証していない。
- 安全な管理者パスワードを環境設定で注入する。今回の検証用パスワードは実行中のみ使用し、共有・保存していない。現行の稼働中プロセスの設定変更は行っていない。
- 管理者認証にログイン試行制限・MFA・明示的なログアウトは未搭載。公開前に管理画面へのアクセス制限とログイン試行制限をプロキシ等で設定。Basic認証はブラウザに認証が残るため共有端末では使わない。
- 送信制限はプロセス内メモリ・接続元IP単位。再起動でリセットされ、プロキシ経由では利用者が同一IPになる。公開構成で制限を調整する。完全なBot対策ではない。
- 通信断で「DB保存済みだが応答だけ届かない」場合、再送で重複する可能性がある。厳密な重複防止は未実装。管理者は氏名・メール・時刻を照合する。
- DBは暗号化されていない。管理者・ホスト運用者は読み取り可能。公開基盤のディスク暗号化、バックアップの暗号化、アクセス制限が必要。
- 対応終了から90日を目安とした削除は手動運用。自動削除・画面からの削除は未実装。バックアップも同じ保持方針で管理する。
- 運営者名・問い合わせ先・プロフィールの事実確認、削除担当、手動メール対応の体制を確定する。メール通知・自動返信は未実装。
- 今回はローカルの機能・基本的な保護の確認。公開インフラの設定審査、負荷試験、第三者による包括的なセキュリティ診断は未実施。

## 再実行

```sh
npm test
```

実ブラウザ検証にはPlaywrightとChromiumが必要。アプリ自体の依存関係は増やしていない。このクラウド環境の既存ツールを使う場合：

```sh
PLAYWRIGHT_MODULE=/opt/codex/cua_node/lib/node_modules/playwright node scripts/verify-browser.cjs
```

スクリーンショットは標準で一時ディレクトリ内の `money-prelaunch-artifacts` に保存する。`REPORT_DIR` で変更可能。保存される申込画面は架空データのみ。検証は新規一時DBを使い、終了時に削除する。
